# 사용자 버그 신고와 운영자 신고함

사용자가 제출한 신고를 운영자가 모아 보는 기능이다. 기존 개인용 `문제 기록`·개발 QA·오류 로그는 그대로 유지한다. 대화·장기기억 암호화를 끄지 않으며, 새 신고의 설명·기대 결과·선택 첨부도 기존 AES-256-GCM 변환기로 암호화해 저장한다.

## 사용자 화면

1. **내 포켓 → 포켓 열기**로 이동한다.
2. 특정 답변 문제라면 답변 아래 **버그 신고**를 누른다. 일반적인 Pocket 기능 문제는 데스크톱 오른쪽 도구 또는 모바일 **포켓 메뉴 → 버그 신고**에서 작성한다.
3. 문제 종류와 설명을 입력한다. 기대 결과는 선택 사항이다.
4. 특정 답변을 신고할 때만 **선택한 답변과 신고 시점의 바로 앞 사용자 메시지를 운영자에게 함께 보내기**를 선택할 수 있다. 기본은 해제다. 선택하지 않으면 작성한 설명과 신고 위치만 제출한다.
5. **운영자에게 신고 보내기**를 누르면 신고 번호가 표시되고 운영자 신고함에 접수된다. 작성한 설명은 운영자에게 전달되므로 비밀번호·API 키 등 비밀은 적지 않는다.

공유에 동의한 경우에도 선택한 버전의 답변과 바로 앞 USER 메시지만 첨부한다. 사용자 입력 최대 2,000자, 답변 최대 12,000자이며 초과 부분은 생략 표시한다. 전체 대화, AI 생성 맥락, 장기기억, QA 진단 덤프는 자동 첨부하지 않는다. 앞 사용자 메시지는 신고 시점의 참고값이며 생성 당시 원본이라고 주장하지 않는다.

신고는 대화와 독립된 사본으로 남는다. 이후 대화 삭제·리롤로 접수 기록이 사라지지 않는다. 네트워크 재시도의 요청 ID가 같으면 같은 접수 번호를 반환한다. 사용자별 시간당 최대 20건으로 제한하며 회원 행 잠금으로 동시에 들어오는 신고도 직렬 처리한다.

## 운영자 화면

ADMIN 또는 DEVELOPER 계정으로 Pocket을 열고 데스크톱 도구 또는 모바일 포켓 메뉴의 **운영자 신고함**을 누른다. 본인 포켓과 무관하게 모든 사용자가 제출한 신고가 이곳에 모인다. 기존 비공개 로그인 모드에서는 기존 계정/이메일 인증 조건도 그대로 적용된다.

- 목록은 한 번에 50건까지 ID·신고자 내부 번호·신고 위치·분류·상태·시각·첨부 유무만 조회한다. 목록을 열 때 본문을 일괄 복호화하지 않는다.
- 신고를 선택하면 해당 신고 설명과 사용자가 동의한 첨부만 복호화해 보여준다. 다른 대화나 장기기억을 추가 조회하지 않는다.
- **접수 → 확인 중 → 처리 완료**로 상태를 변경하고 상태별로 필터링할 수 있다. 이전 신고는 버튼으로 추가 조회한다.
- 신고함을 열어 둔 동안 새 신고가 들어오면 **새로고침**으로 목록을 갱신한다.
- 서버는 로그인 권한뿐 아니라 DB의 현재 회원 역할도 다시 확인한다. 일반 사용자·역할이 회수된 운영자는 조회/상태 변경이 차단된다.
- 목록·내용 열람·상태 변경과 인증된 권한 거부를 기존 `private_data_audit`에 기록한다. 감사 기록에는 신고 본문·대화·키를 넣지 않는다. 감사 저장에 실패하면 본문 반환을 차단한다. 원래 사용자 대화의 임의 복호화 API에 필요한 별도 허용 목록은 변경하지 않는다.

이 기능은 사이트 내부 신고함이다. 이메일·Slack 등 외부 알림은 발송하지 않는다.

## API

- `POST /api/worlds/pockets/{sessionId}/bug-reports`: 로그인한 본인의 포켓에서만 제출. `requestId` UUID, `category`, 필수 `problem`(5,000자 이하), 선택 `expected`(5,000자 이하), 선택 `messageId`/`variantNo`, 기본 false인 `shareContext`를 받는다. 응답은 ID·상태·접수 시각뿐이다.
- `GET /api/admin/bug-reports?before={id}&status={NEW|REVIEWING|RESOLVED}`: 운영자용 메타데이터 목록.
- `GET /api/admin/bug-reports/{id}`: 운영자용 단일 신고 내용.
- `PUT /api/admin/bug-reports/{id}/status`: 운영자용 상태 변경. 본문 예: `{"status":"REVIEWING"}`.

응답은 `Cache-Control: no-store`로 처리한다. 본인 포켓인지 확인하기 전에 첨부 대화를 읽지 않는다. 클라이언트가 신고자를 지정하거나 다른 포켓의 메시지/버전을 첨부할 수 없다.

## 운영 반영

운영 DB 변경이나 배포는 이 작업에서 실행하지 않는다. 먼저 기존 암호화 운영 문서의 백업·복원 검증 절차를 완료한다.

1. 기존 암호화 준비 SQL을 아직 적용하지 않았다면 복제 DB에서 먼저 검증한다. 운영자 감사 테이블 `private_data_audit`가 필요하다.
2. 복제 DB에서 `deploy/sql/20261029-bug-reports.sql`로 새 `bug_reports` 테이블을 만든다. 애플리케이션이 자동으로 운영 스키마를 변경하지 않는다.
3. 기존과 동일한 외부 암호화 키를 주입한다. 신고용 별도 평문 저장이나 키 변경은 하지 않는다.
4. 일반 사용자 신고 → 운영자 목록/본문 확인 → 상태 변경 → 타인/일반 사용자 접근 차단을 검증한다. DB에서 `problem`, `expected`, `evidence_json`이 `enc:v2:` 암호문인지 확인한다. 동의하지 않은 신고의 `evidence_json`은 NULL이어야 한다.
5. 검증 후에만 운영에 같은 절차로 반영한다. 새 테이블의 3개 암호화 필드는 기존 `EncryptedColumns` 목록과 마이그레이션 검증에도 포함된다. 따라서 최신 마이그레이션 CLI를 실행하기 전 새 테이블을 먼저 준비한다.

기존 평문 QA/오류 기록을 이 신고함으로 자동 복사하거나 과거 기록을 일괄 공개하지 않는다.
