# 이번 주 개발 순서

2026-09-23 기준. 각 단계는 구현·자동 검증 후 사용자 RP/UX QA를 거쳐 다음 단계로 진행한다.

| 순서 | 범위 | 완료 판단 |
|---|---|---|
| 1 | 채팅 장기기억 저장·회상 | 최근 대화에서 빠진 정보를 회상하고, 출처·대화방 경계·중복 방지가 확인됨 |
| 2 | 재접속 자동 행동 | 캐치업 호출 연결, 처리 구간 중복 방지, 결과 조회 및 중요한 선택의 정지 경계 확인 |
| 3 | 캐릭터 메이킹 UI | 상세 설정 자동 생성·수정·저장, 이후 장르/태그/이미지 등 세부 요구사항을 작은 단계로 처리 |
| 4 | 월드 메이킹 UI | 월드 기본 설정 생성·수정·저장, 캐릭터 연결 및 대화 컨텍스트 반영 |

## 현재 체크포인트: 재접속 자동 진행 1차 QA 통과, 대화 상태 변화 QA 준비

- 사용자의 명시적 발언에서 Lite가 최대 3개 기억 후보를 고른다. 원문 인용을 저장해 발언 사실과 실제 세계의 사실을 구분한다.
- `*행동·속마음 지문*`과 OOC는 첫 저장 대상에서 제외한다. 기존 대화의 일괄 기억 변환은 수행하지 않는다.
- 대화방 및 출처 메시지를 기록한다. 같은 방의 동일 인용은 공백을 정규화한 해시로 중복을 막는다. 바꿔 말한 문장의 의미상 중복 병합은 후속 과제다.
- 현재 발언과 기억의 문자열 겹침, 기억 강도, 시각 순으로 최대 5개를 회상한다. 벡터/의미 검색 및 기억 정정·대체 관리는 후속 과제다.
- 기억 추출은 DB 쓰기 트랜잭션 밖에서 진행하고, 실패해도 저장된 채팅 응답은 반환한다.
- Inspector의 `MEMORY`를 펼치면 이번 응답에 사용한 기존 기억과 다음 턴부터 사용할 새 기억을 구분해 볼 수 있다.
- `SAVED`: 새 기억 저장. `NONE`: 새 후보 없음 또는 동일 인용 중복. `SKIPPED`: 발언 없음/보수적 제외/4,000자 초과. `FAILED`: 추출 또는 저장 실패. `DISABLED`: 설정으로 중단.
- `GEMINI_MEMORY_MODEL` 기본값은 `gemini-3.5-flash-lite`. 발언이 있는 적격 턴에 최대 1회 호출하며 자동 재시도는 없다. `CHAT_MEMORY_ENABLED=false`로 신규 저장 호출을 끌 수 있다. 기존 기억 회상은 유지된다.
- JPA `memories`에 nullable 대화방/출처 메시지/중복 키가 추가된다. 기존 `ddl-auto=update` 설정에 따라 애플리케이션 재시작 시 반영된다.

## 자동 검증 결과

선별한 기억·시간·재접속·대화 상태 테스트 61개 통과(2026-09-23). H2 격리 DB에서 기억 저장·방 분리·최근 20개 메시지 밖의 기억 주입, 동시 재접속 시 단일 처리, 3일 상한, 채팅 중 충돌 차단, 네트워크 복구 후 전송 시 부재 반영을 확인했다. 이번 단계에서는 JSON 본문/추론 분리, 잘못된 상태 제안 거절, 0~100 범위, 중복·만료 요청 차단, 방별 상태 보존 및 감소한 에너지로 야간 휴식 발동까지 확인했다. 프런트 빌드 통과, lint 기존 경고 3개, git diff --check 통과. 실제 Gemini 호출 및 사용자 MySQL 서버 재시작은 수행하지 않았다.

## 사용자 QA

1. 백엔드 재시작 후 `내 반려묘 이름은 감자야. 나는 복숭아 알레르기가 있어.` 입력. MEMORY가 SAVED이고 저장 목록에 원문 발언이 있는지 확인.
2. 다음 턴 `내 반려묘 이름이 뭐였지? 먹으면 안 되는 과일도 기억해?` 입력. 회상 목록과 실제 답변을 함께 확인.
3. 1번 발언을 그대로 다시 입력. 같은 원문 인용이면 새 저장은 0개여야 한다. 추출 모델이 다른 길이의 인용을 선택하면 의미상 중복은 발생할 수 있다.
4. `*표정을 바꾸지 않고 속으로만 '노란 수첩을 사야겠다'고 생각했다.*` 입력. SKIPPED/저장 0개여야 한다. 캐릭터가 숨긴 생각을 아는지는 별도로 RP QA한다.
5. 장기 회상 QA는 새 대화에서 표식을 말한 뒤 다른 이야기로 11턴 이상 대화하고 다시 묻는다. 중간에 표식이 반복되면 최근 메시지 효과가 섞이므로 마지막 언급 이후 11턴을 센다. 자동 검증은 이미 최근 메시지 제외 조건을 충족했지만 실제 응답 품질은 별도 확인한다.

QA 전에는 시트 진행도를 확정 상향하지 않는다.

## 재접속 자동 진행 1차 연결

- 사용자 프로필 선택·변경·재입장 및 텍스트 설정(파란 외투)의 대화 반영은 사용자 QA 통과.
- 방별 `자동 진행 ON/OFF`를 추가했다. 기존 방과 새 방 모두 기본 OFF이며 켠 시점 이전 부재는 소급하지 않는다.
- 채팅 진입 및 숨겨진 탭에서 복귀할 때 처리한다. 표시 중인 탭은 30초마다 접속 상태만 갱신한다. 1분 미만 재입장은 진행하지 않으며 부재 추정에는 최대 약 30초의 차이가 있을 수 있다. 탭이 보이지만 다른 앱에 가려진 경우는 브라우저 visibility 판정에 따른다.
- 실제 접속 시각과 RP 시각을 분리해 부재 기간만 RP 현재 시각에 더한다. 회당 최대 3일이며 초과분은 이월하지 않는다.
- 기존 야간(22~06시)·에너지 50 미만 휴식 규칙만 연결했다. 상태 70인 새 방에서는 조건을 충족하지 않아 시간만 흐르는 것이 정상이다. 1차 연결 당시에는 일반 대화에 따른 상태 변화가 없었으며, 아래 단계에서 연결한다.
- AI 판단 또는 허용하지 않은 행동 후보가 있는 구간은 상태·시간을 진행하기 전에 보류한다. 이번 단계는 중요한 분기의 선택지 UI/판단 모델까지 완성한 것이 아니다. 보류 뒤 대화는 가능하며 OFF→ON으로 재개해도 같은 조건이 남아 있으면 다시 보류된다.
- 계산에는 방별 상태 복사본을 쓰고 공용 CharacterState/관계를 변경하지 않는다. 휴식은 해당 방의 메시지·경험 기억에 저장하며, 최근 처리 구간/행동/보류 사유는 재접속 후에도 조회할 수 있다.
- 방 잠금 안에서 결과·시간·접속 체크포인트를 함께 커밋한다. 채팅 생성 중 표시는 짧은 트랜잭션으로 관리하고 외부 AI 호출 동안 DB 잠금은 잡지 않는다. 처리 표시의 10분 만료 후 이전 요청의 늦은 응답은 저장을 거절한다.
- 캐치업 자체에는 Gemini 호출이 없다. 새로운 테이블 `conversation_catch_ups`와 Conversation의 접속/설정 필드는 기존 ddl-auto=update로 재시작 시 반영된다. 서버를 직접 재시작하지 않았다.
- 후속: 장면 의미에 맞는 AI 행동, 감정/에너지 변화, 중요한 선택 제시·재개, 세계/관계 통합. 이번 QA 뒤 다음 작은 단계의 범위를 정한다.

### 이번 사용자 QA

1. 백엔드 재시작 후 기존 방에 입장한다. 기본 OFF 상태에서 외출·재입장해도 RP 시간이 그대로인지 확인한다.
2. ON으로 켜고 캐릭터 목록으로 나가 2분 이상 기다린 뒤 같은 캐릭터를 연다. `최근 자동 진행`을 펼쳐 RP 시간이 부재만큼 늘었는지 확인한다. 이어 `지금 몇 시인가요?`로 응답 시간도 확인한다.
3. 바로 새로고침한다. 직전에 처리한 구간이 재가산되지 않아야 한다. 화면을 켜 둔 채 2분 읽은 뒤 새로고침해도 그 시간이 추가되지 않아야 한다.
4. OFF로 바꾸고 2분 후 재입장한다. 시간이 늘지 않아야 한다. 새 대화는 OFF·별도 시간으로 시작하며 이전 방의 자동 진행 결과/기억이 표시되지 않아야 한다.

## 대화에 따른 에너지·기분 변화

- 앞 단계 사용자 QA: 약 4분 부재 반영 확인, 즉시 새로고침 시 중복 가산 없음, OFF 재입장 시 시간 유지 확인. 재접속 1차 QA 통과로 기록한다.
- 이번 범위는 대화 상태 변화 한 단계다. 새로운 자동 행동 종류나 중요한 분기 선택 UI는 추가하지 않는다.
- Gemini의 기존 대화 생성 요청 한 번에서 `reply`와 상태 제안을 JSON으로 함께 받는다. 화면과 메시지 DB에는 RP 본문만 저장하며, 추가 AI 호출은 없다. 상태 지시문·메타데이터에 따른 토큰 증가는 있다.
- 에너지·기분은 턴당 각각 -10~+10 제안만 허용하고 최종 값은 0~100으로 제한한다. 각 비영(0이 아닌) 변화에는 응답 본문의 정확한 인용 근거가 필요하다. 평범한 인사·기존 피로의 반복·유저 자신의 피로·계획·속마음·수치 조작 지시는 변동 원인으로 삼지 않도록 모델에 지시한다.
- 서버는 형식/정수/범위/본문 인용 존재를 검증한다. 인용이 실제로 타당한 새 원인인지, 숨긴 생각의 영향을 받지 않았는지까지 의미적으로 보장하지 않으므로 실제 RP QA가 필요하다.
- 본문이 유효하고 상태 제안만 잘못되면 대화는 저장하되 상태를 유지한다(`REJECTED`). 본문 JSON이 깨졌거나 차단/중단된 응답은 저장하지 않으며 파싱 때문에 유료 재호출하지 않는다.
- 메시지와 방별 상태는 같은 짧은 트랜잭션에서 저장한다. 만료되거나 이미 완료된 요청은 다시 적용되지 않는다. 공용 CharacterState와 다른 방은 바꾸지 않는다. 바뀐 상태는 다음 대화 컨텍스트와 기존 재접속 휴식 규칙에 사용한다.
- 상단 `현재 상태`는 새로고침 후에도 DB 값을 보여준다. 턴별 `STATE` Inspector는 APPLIED/UNCHANGED/REJECTED, 이전/이후 수치와 근거를 표시한다. 이 상세 Inspector는 해당 응답 시점의 정보이며 별도 이력 저장은 이번 범위가 아니다.
- 자동 진행 OFF는 부재 시간 진행을 끄는 설정이다. 대화 중 상태 변화는 계속 반영된다. 기존 자동 진행 보류는 수치가 회복돼도 임의로 해제하지 않으며 OFF→ON 후 다시 판단한다.
- 새 DB 컬럼은 필요 없다. 서버 직접 재시작·실제 유료 모델 호출·커밋/푸시는 이번 단계에서 수행하지 않는다. 변경 파일과 검증 기록을 검토 가능한 워킹 트리로 남긴다.

### QA 오류 수정: 일반 RP 응답의 JSON 파싱 실패

- 사용자 로그에서 `*`로 시작하는 본문을 JSON 객체로 파싱하다 실패한 것을 확인했다. MIME 지정과 프롬프트만 믿고 일반 RP 응답까지 실패 처리한 경로를 보완했다.
- [공식 Generate Content 구조화 출력 문서](https://ai.google.dev/gemini-api/docs/generate-content/structured-output?hl=en)의 REST `generationConfig.responseFormat.text` 형식으로 MIME과 필수 필드 스키마를 전달한다.
- 정상 종료된 일반 RP 본문 및 JSON 문자열은 본문을 보존하고 상태 제안은 REJECTED로 처리한다. 완전한 JSON 코드블록은 외곽만 제거한다. 깨진 객체/배열, 메타데이터가 섞인 평문, 차단/중단 응답은 그대로 노출하지 않는다. 복구용 AI 재호출은 없다.
- 관련 테스트 28개(파서·상태 검증·방 저장·기억 회귀) 통과, Java 컴파일 및 diff 공백 검사 통과. 실제 모델 출력 재확인은 사용자 QA로 진행한다.
- 후속 QA의 HTTP 400 원인: 예제의 MIME 문자열을 새 `responseFormat.text.mimeType`에 사용했으나 실제 필드는 enum이다. [Google v1beta discovery 명세](https://generativelanguage.googleapis.com/$discovery/rest?version=v1beta)의 `TextResponseFormat`에서 확인한 `APPLICATION_JSON`으로 수정했다. 기존 `responseMimeType`과 새 필드의 값 형식을 혼동하지 않도록 요청 테스트도 수정했다.

### 이번 상태 변화 QA

1. 백엔드 재시작 후 `안녕하세요.`처럼 평범한 인사. RP 본문에 JSON/상태 메타데이터가 보이지 않고 현재 상태와 STATE가 표시되는지 확인한다. 단순 인사 자체로 수치가 계속 깎이면 오류다.
2. 실제로 상대 캐릭터가 일을 마친 장면으로 대화한다. 예: `*마르바스와 함께 무거운 서류 상자를 여러 차례 옮겼다. 작업이 끝나자 그에게 물을 건넸다.* 고생하셨어요.` 상대가 실제로 지쳤다는 반응이면 에너지 감소와 해당 본문 근거를 함께 확인한다. 감소량은 고정값이 아니다.
3. 상대가 실제 휴식을 취하도록 장면을 이어간다. 쉬자고 제안만 했는데 즉시 회복시키는지, 실제 쉬는 행동 이후 회복하는지 구분한다. 칭찬·격려도 실제 새 감정 반응이 있을 때 기분 변화가 가능한지 확인한다.
4. `*표정과 자세를 유지한 채 속으로만 그를 비난했다.*` 또는 `나중에 같이 운동할까요?`를 입력한다. 숨긴 생각과 아직 하지 않은 운동만으로 수치가 변하면 보강 대상이다. 단, 공개된 제안 자체에 대한 실제 감정 반응은 별도로 판단한다.
5. 새로고침 후 상태 유지 → 다른 방 영향 없음 → 새 대화의 70/70 초기화 확인. 이후 에너지 50 미만/야간 조건에서 ON으로 2분 부재 후 휴식이 발동하는 연결은 자동 테스트로도 확인한다.

## 1단계 실제 QA 이후 표현 보강

- 사용자 결과: 저장 2개, 동일 발언 재입력 시 저장 0개, 속마음 지문 저장 제외 확인. 복숭아 알레르기는 11턴 이상 후 맥락에 맞게 회상했다. 감자는 중간에 반복 언급되어 장기기억 단독 검증은 보류하며, 친밀한 반려동물 언급 자체는 오류로 취급하지 않는다.
- 발견: 영어/한국어 혼용, 감자를 Potato로 번역, 속마음의 수첩 및 유머 센스에 직접 반응, 기억을 입력 데이터처럼 묘사하는 표현.
- 이번 보강: 한국어 기본 출력과 명시적인 캐릭터 언어 설정을 구분하고 고유명사를 보존한다. 지문 표기를 재명시하고, 속마음의 직접 인용뿐 아니라 관련 화제 유도도 제한한다. 회상 순위는 유지하며 대사 생성용 기억 입력에서 중요도/강도 숫자만 제거한다.
- 프롬프트 보강이므로 출력 준수를 서버가 강제 보장하지는 않는다. 기존 오류가 대화 이력에 남아 있으므로 새로운 비밀 대상어로 재시험한다. 캐릭터의 자연스러운 표정 해석과 설정상 상담 기록 행위는 허용한다.

## QA 편의: 같은 캐릭터로 새 대화 시작

- 채팅 상단 `새 대화 시작` → 확인 후 `POST /api/chat/{characterId}/conversations`로 새 방과 인트로를 함께 저장한다. Gemini 호출은 없다.
- 캐릭터 설정·예시·인트로는 재사용한다. 이전 메시지·방별 기억·공용 사건 기억·공용 관계는 새 방 컨텍스트로 가져오지 않는다. 이전 데이터는 삭제하지 않는다.
- 시작 시각은 서버 현재 시각, 에너지·기분은 각각 기본값 70. 새 방 상태는 Conversation에 보관하고 기존 CharacterState는 변경하지 않는다. 독립 방의 관계/자동 행동 연결은 이후 개발 범위다.
- 현재 API는 캐릭터별 가장 최근에 생성한 방을 사용한다. 새로고침·캐릭터 목록 재진입도 최신 방을 연다. 이전 방 선택/복귀 UI는 후속 작업이다.
- 전송/초기 조회/방 생성 중 버튼을 비활성화하고 같은 화면의 중복 요청을 막는다. 취소는 변경하지 않으며 생성 성공 시 입력창·Inspector를 비운다.
- 재시작 시 기존 ddl-auto=update로 Conversation의 nullable 독립 시작/에너지/기분 필드가 추가된다.
- QA: 취소 시 기존 화면 유지 → 확인 시 인트로만 표시 → 과거 개인 정보 질문 시 회상 0개 → 새 정보 저장·회상 → 새로고침 후 새 방 유지 확인.

## 우선순위 변경: 유저 캐릭터 프로필 최소 기능

자동 행동 연결에 앞서 유저 프로필을 도입한다. 근거는 구현 내용 시트 C96:F98 및 사용자의 이미지 인식 제외 요청이다.

- 프로필 목록, 생성, 수정, 대화방별 선택을 제공한다. 이름(최대 40자)과 설정의 합계는 500자, 로컬 공용 목록은 최대 10개다. 계정별 소유권은 로그인 도입 때 연결한다.
- 프로필 미지정 방은 첫 전송 전에 선택해야 한다. 기존 방 입장은 저장된 선택을 재사용하며, 새 대화 시작은 프로필 선택 후 생성한다. 채팅 상단 `나: 이름`에서 변경한다.
- 설정 수정은 그 프로필을 참조하는 방들에 반영된다. 프로필 선택 변경은 해당 방에만 적용한다. 기존 대화·기억을 다른 인물에 맞게 변환하는 기능은 후순위다.
- Gemini에는 이름·설정 텍스트만 전달한다. 사진 데이터와 URL은 보내지 않는다. 사진은 화면 표시용 선택 항목이며 280KB 이하 PNG/JPEG/WebP를 받는다.
- 이미지에서 설정 초안 만들기, 유료 프로필 이미지 생성, 정교한 배치는 후속 과제다.
- 새 `player_profiles` 테이블 및 `conversations.player_profile_id`는 기존 ddl-auto=update로 재시작 시 추가된다.
- QA: 이름 하린/설정 '검은 단발머리. 도서관 사서. 파란 외투를 입었다.'로 생성·선택 → 외투 색/이름 관련 RP 확인 → 프로필 변경 → 다음 응답 반영 → 새로고침 후 선택 유지. 이미지에만 있는 특징은 AI가 인식하지 않아야 한다.
